# Frontend UI Engineering

## Overview

Build production-quality user interfaces that are accessible, performant, and visually polished using the project's stack: **server-rendered Smarty templates, vanilla JS modules, jQuery for legacy pages, and Vue SFC islands for interactive widgets**. The goal is UI that looks like it was built by a design-aware engineer — not generated by an AI. This means real design system adherence, proper accessibility, thoughtful interaction patterns, and no generic "AI aesthetic."

## When to Use

- Building new pages, partials, or widgets
- Modifying existing user-facing interfaces
- Implementing responsive layouts
- Adding interactivity or client state
- Fixing visual or UX issues

## Component Architecture

### File Structure

Colocate everything related to a UI component:

```
templates/
  partials/
    task-list.tpl              {* Smarty partial — the reusable unit *}
    task-item.tpl
public/
  js/
    modules/
      task-list.js             // vanilla JS behavior for the partial
  vue/
    TaskFilter.vue             // Vue island for a rich widget
src/
  Http/
    Controllers/
      TaskController.php       // PHP controller that renders the partial
```

One partial = one responsibility. Name partials after what they render, not where they appear.

### Smarty Partial Patterns

Prefer **composition** by `{include}`ing focused partials, not configuration flags that change the output shape.

```smarty
{* GOOD: composable partials *}
{include file="partials/card.tpl" title="Tasks"}
  {include file="partials/task-list.tpl" tasks=$tasks}
{/include}

{* AVOID: one mega-partial driven by booleans *}
{include file="partials/card.tpl"
  title="Tasks" headerVariant="large" bodyPadding="md" showFooter=true content=$tasks}
```

**Keep partials focused and escape every variable:**

```smarty
{* partials/task-item.tpl *}
<li class="task-item" data-task-id="{$task.id|escape}">
  <input type="checkbox"
         class="js-toggle"
         {if $task.done}checked{/if}
         aria-label="Mark {$task.title|escape} as done">
  <span class="task-item__title {if $task.done}task-item__title--done{/if}">
    {$task.title|escape}
  </span>
  <button type="button" class="js-delete btn btn--ghost" aria-label="Delete task">
    <svg aria-hidden="true">...</svg>
  </button>
</li>
```

**Separate data loading from rendering** — the controller prepares data, the template renders it. Templates should not call services or run queries.

```php
// src/Http/Controllers/TaskController.php
public function index(): string
{
    $tasks = $this->taskService->listForUser($this->session->userId());

    return $this->view->fetch('pages/tasks.tpl', [
        'tasks'    => $tasks,
        'isEmpty'  => $tasks === [],
        'pageSize' => 20,
    ]);
}
```

```smarty
{* pages/tasks.tpl *}
{if $isEmpty}
  {include file="partials/empty-state.tpl"
           icon="tasks"
           title="No tasks yet"
           body="Get started by creating a new task."}
{else}
  {include file="partials/task-list.tpl" tasks=$tasks}
{/if}
```

## Vanilla JS Modules and jQuery

### Vanilla JS — event delegation, data attributes

Prefer small, focused modules. Use data attributes (`data-*`) as the contract between template and JS — avoid coupling to CSS class names that may change.

```javascript
// public/js/modules/task-list.js
export function initTaskList(root) {
  // Event delegation: one listener handles every future item
  root.addEventListener('click', async (e) => {
    const toggle = e.target.closest('.js-toggle');
    if (toggle) {
      const item = toggle.closest('[data-task-id]');
      await toggleTask(item.dataset.taskId, toggle.checked, item);
      return;
    }
    const del = e.target.closest('.js-delete');
    if (del) {
      const item = del.closest('[data-task-id]');
      if (confirm('Delete this task?')) {
        await deleteTask(item.dataset.taskId, item);
      }
    }
  });
}

async function toggleTask(id, done, item) {
  item.setAttribute('aria-busy', 'true');
  try {
    const res = await fetch(`/api/tasks/${id}`, {
      method: 'PATCH',
      headers: { 'Content-Type': 'application/json', 'X-CSRF-Token': window.CSRF },
      body: JSON.stringify({ done }),
    });
    if (!res.ok) throw new Error('Request failed');
    item.classList.toggle('task-item--done', done);
  } catch (err) {
    console.error(err);
    item.querySelector('.js-toggle').checked = !done; // revert optimistic UI
    alert('Could not save. Please try again.');
  } finally {
    item.removeAttribute('aria-busy');
  }
}
```

Bootstrap the module on the pages that need it:

```javascript
document.querySelectorAll('[data-component="task-list"]').forEach(initTaskList);
```

### jQuery — legacy pages

For pages that already use jQuery, stay idiomatic — don't mix styles within one file.

```javascript
// public/js/legacy/task-list.jquery.js
(function ($) {
  'use strict';

  $(document).on('click', '.js-toggle', function () {
    var $item = $(this).closest('[data-task-id]');
    var done  = this.checked;

    $item.attr('aria-busy', 'true');
    $.ajax({
      url: '/api/tasks/' + $item.data('task-id'),
      method: 'PATCH',
      contentType: 'application/json',
      headers: { 'X-CSRF-Token': window.CSRF },
      data: JSON.stringify({ done: done }),
    })
      .done(function () {
        $item.toggleClass('task-item--done', done);
      })
      .fail(function () {
        $item.find('.js-toggle').prop('checked', !done);
        alert('Could not save. Please try again.');
      })
      .always(function () {
        $item.removeAttr('aria-busy');
      });
  });
})(jQuery);
```

**Always delegate** (`$(document).on('click', '.js-…')`) rather than binding directly — it survives DOM replacement after AJAX.

### Vue SFC Islands

Use Vue for rich interactive widgets (filters, editors, dashboards) embedded into an otherwise server-rendered page. Mount each widget as an isolated island, not a full SPA.

```vue
<!-- public/vue/TaskFilter.vue -->
<script setup>
import { ref, computed, watch } from 'vue';

const props = defineProps({
  initialTasks: { type: Array, required: true },
});

const query    = ref('');
const priority = ref('all');

const filtered = computed(() =>
  props.initialTasks.filter((t) => {
    const matchesQuery = t.title.toLowerCase().includes(query.value.toLowerCase());
    const matchesPrio  = priority.value === 'all' || t.priority === priority.value;
    return matchesQuery && matchesPrio;
  })
);

watch([query, priority], () => {
  // Persist filter in the URL so it is shareable and survives refresh
  const params = new URLSearchParams(window.location.search);
  params.set('q', query.value);
  params.set('priority', priority.value);
  window.history.replaceState({}, '', '?' + params.toString());
});
</script>

<template>
  <div class="task-filter">
    <label class="sr-only" for="task-search">Search tasks</label>
    <input id="task-search" v-model="query" type="search" placeholder="Search…">

    <label class="sr-only" for="task-priority">Priority</label>
    <select id="task-priority" v-model="priority">
      <option value="all">All priorities</option>
      <option value="low">Low</option>
      <option value="medium">Medium</option>
      <option value="high">High</option>
    </select>

    <ul class="task-list">
      <li v-for="t in filtered" :key="t.id">{{ t.title }}</li>
    </ul>
  </div>
</template>
```

Mount the island from a tiny bootstrap:

```javascript
// public/js/islands/task-filter.js
import { createApp } from 'vue';
import TaskFilter    from '../../vue/TaskFilter.vue';

document.querySelectorAll('[data-island="task-filter"]').forEach((el) => {
  const initialTasks = JSON.parse(el.dataset.tasks);
  createApp(TaskFilter, { initialTasks }).mount(el);
});
```

And the template rehydrates server state safely via a JSON data attribute:

```smarty
<div data-island="task-filter"
     data-tasks='{$tasksJson|escape:"htmlall"}'></div>
```

> Server-generated JSON embedded in HTML must be escaped with `htmlall` (or
> `htmlspecialchars($json, ENT_QUOTES)`) — not treated as raw JS.

## State Management

Choose the simplest approach that works:

```
Server-rendered HTML           → Default. Smarty re-renders on POST/redirect.
URL state (?params)            → Filters, pagination, sort order (shareable).
Data attributes on the DOM     → Per-element state read by vanilla JS.
Vue reactive refs (ref/reactive) → Per-island interactive state.
Global JS object (window.App)  → Small app-wide constants (CSRF, current user).
Server state via fetch()       → Lists/details that need live refresh.
```

**Rehydrate server state into islands via JSON script tags**, never by scraping the DOM:

```smarty
<script type="application/json" id="bootstrap-data">
  {$bootstrap|json_encode nofilter}
</script>
```

```javascript
const data = JSON.parse(document.getElementById('bootstrap-data').textContent);
```

**Avoid coupling the Vue island to the rest of the page's jQuery code.** If they must communicate, use `CustomEvent` on `document`, not shared globals.

## Design System Adherence

### Avoid the AI Aesthetic

AI-generated UI has recognizable patterns. Avoid all of them:

| AI Default | Why It Is a Problem | Production Quality |
|---|---|---|
| Purple/indigo everything | Models default to visually "safe" palettes, making every app look identical | Use the project's actual color palette |
| Excessive gradients | Gradients add visual noise and clash with most design systems | Flat or subtle gradients from the design system |
| Rounded everything (border-radius 16px+) | Max rounding signals "friendly" but ignores real corner-radius hierarchy | Consistent radius tokens from the system |
| Generic hero sections | Template-driven layout disconnected from actual content or user need | Content-first layouts |
| Lorem ipsum copy | Hides length/wrapping/overflow problems that real content reveals | Realistic placeholder content |
| Oversized padding everywhere | Equal generous padding destroys visual hierarchy | Consistent spacing scale |
| Stock card grids | Uniform grids ignore information priority and scanning patterns | Purpose-driven layouts |
| Shadow-heavy design | Layered shadows compete with content and slow low-end devices | Subtle or no shadows unless the system specifies |

### Spacing and Layout

Use a consistent spacing scale from your CSS tokens. Don't invent pixel values:

```css
/* GOOD — use design tokens */
.card { padding: var(--space-4); gap: var(--space-3); }

/* BAD — off-scale magic numbers */
.card { padding: 13px; margin-top: 2.3rem; }
```

### Typography

Respect the type hierarchy:

```
h1  → Page title (one per page)
h2  → Section title
h3  → Subsection title
p   → Default body text
small / .text-muted → Secondary/helper text
```

Don't skip heading levels. Don't use heading styles for non-heading content.

### Color

- Use semantic CSS custom properties: `--color-text`, `--color-surface`, `--color-border`
- Ensure contrast: 4.5:1 for normal text, 3:1 for large text
- Don't rely solely on color — add icons, text, or patterns

## Accessibility (WCAG 2.1 AA)

### Keyboard Navigation

```smarty
{* GOOD: native button is focusable and activates on Enter/Space *}
<button type="button" class="js-delete">Delete</button>

{* BAD: a div is not focusable and has no keyboard semantics *}
<div class="js-delete" onclick="delete()">Delete</div>
```

Use the right element for the job: `<button>` for actions, `<a href>` for navigation, `<input>` / `<select>` / `<textarea>` for form fields. Role/tabindex/keyboard hacks are a last resort.

### ARIA Labels

```smarty
{* Icon-only button needs an accessible name *}
<button type="button" aria-label="Close dialog">
  <svg aria-hidden="true">...</svg>
</button>

{* Every input has a label *}
<label for="email">Email</label>
<input id="email" type="email" required>

{* Or aria-label when no visible label exists *}
<input type="search" aria-label="Search tasks">
```

### Focus Management

When a dialog opens, move focus to the first interactive element and trap focus until it closes:

```javascript
export function openDialog(dialog) {
  const previouslyFocused = document.activeElement;
  dialog.hidden = false;
  dialog.querySelector('[autofocus], button, input, [tabindex]')?.focus();

  dialog.addEventListener('keydown', (e) => {
    if (e.key === 'Escape') closeDialog(dialog, previouslyFocused);
  });
}
```

### Meaningful Empty, Loading, and Error States

Never show a blank screen. Every list, fetch, and form must handle all three states.

```smarty
{if $isLoading}
  <div role="status" aria-live="polite" class="task-list__skeleton">Loading tasks…</div>
{elseif $error}
  <div role="alert" class="task-list__error">
    Couldn't load tasks. <button type="button" class="js-retry">Retry</button>
  </div>
{elseif $tasks|@count === 0}
  {include file="partials/empty-state.tpl"
           title="No tasks yet" body="Get started by creating a new task."}
{else}
  {include file="partials/task-list.tpl" tasks=$tasks}
{/if}
```

## Responsive Design

Mobile first. Use CSS custom media queries and a single breakpoint scale:

```css
.task-grid {
  display: grid;
  grid-template-columns: 1fr;           /* mobile */
  gap: var(--space-4);
}
@media (min-width: 48rem) { .task-grid { grid-template-columns: 1fr 1fr; } }
@media (min-width: 64rem) { .task-grid { grid-template-columns: 1fr 1fr 1fr; } }
```

Verify at 320 px, 768 px, 1024 px, and 1440 px via Chrome DevTools device mode.

## Loading and Transitions

Prefer **skeletons over spinners** for content areas, and **optimistic UI** for toggles and edits where the success rate is high. Revert on failure:

```javascript
// Optimistic toggle with revert
checkbox.checked = newValue;
item.classList.toggle('done', newValue);
try {
  await fetch('/api/tasks/' + id, { method: 'PATCH', body: JSON.stringify({ done: newValue }) });
} catch {
  checkbox.checked = !newValue;
  item.classList.toggle('done', !newValue);
  showToast('Could not save — reverted');
}
```

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "Accessibility is a nice-to-have" | It's a legal requirement in many jurisdictions and a quality standard. |
| "We'll make it responsive later" | Retrofitting responsive design is 3× harder than building it from the start. |
| "The design isn't final, so I'll skip styling" | Use the design system defaults. Unstyled UI creates a broken first impression. |
| "This is just a prototype" | Prototypes become production. Build the foundation right. |
| "The AI aesthetic is fine for now" | It signals low quality. Use the real design system from the start. |
| "jQuery is fine to mix with Vue here" | Each island owns its DOM. Crossing the boundary leads to desync bugs. |

## Red Flags

- Smarty partials over 200 lines (split them)
- Inline styles or arbitrary pixel values outside the design tokens
- Missing error / loading / empty states
- No keyboard navigation testing
- Color as the sole indicator of state (red/green without text or icon)
- Generic "AI look" — purple gradients, oversized cards, stock layouts
- Variables rendered without `|escape` in Smarty
- jQuery and Vue mutating the same DOM subtree

## Verification

After building UI:

- [ ] Page renders without console errors or warnings
- [ ] All interactive elements are keyboard accessible (Tab through the page)
- [ ] Screen reader can convey the page's content and structure
- [ ] Responsive at 320 px, 768 px, 1024 px, 1440 px
- [ ] Loading, error, and empty states all handled
- [ ] Follows the project's design system (spacing, colors, typography)
- [ ] Every user-supplied variable in Smarty uses `|escape`
- [ ] No accessibility warnings in axe-core or Lighthouse
